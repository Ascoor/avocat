 
+# الهيكلية الرئيسية للتطبيق (Backend أولًا)

> هذا المستند يقدّم تصورًا عمليًا ومفصلًا لبناء الواجهة الخلفية كنواة للنظام، بحيث تكون إدارة البيانات، الصلاحيات، والتكاملات اهزة قبل التوسع في الواجهة الأمامية.

## 1) المبادئ الحاكمة

- **Domain-first**: تنظيم الكود حول نطاقات العمل (Cases, Clients, Sessions, Finance...) بدل التنظيم حسب نوع الملف فقط.
- **API-first**: كل سلوك عمل يجب أن يكون متاحًا عبر API ثابتة قبل ربطه بالـ Frontend.
- **Secure-by-default**: المصادقة، التفويض، والتدقيق (Audit) ليست إضافات، بل جزء من كل وحدة.
- **Event-driven حيث يلزم**: المهام الثقيلة وغير المتزامنة (إشعارات، معالجة مستندات، تكاملات) تُدار عبر Queue/Jobs.
- **Observability**: تسجيل الأحداث المهمة، قياس الأداء، وتتبّع الأخطاء منذ البداية.

## 2) الطبقات المعمارية المقترحة

### 2.1 طبقة العرض (HTTP/API Layer)
- `routes/api.php`: تعريف المسارات وفق نسخ API (`/api/v1/...`).
- `Controllers`: مسؤولة فقط عن:
  - التحقق الشكلي عبر `FormRequest`.
  - استدعاء خدمات النطاق.
  - إعادة `Resource` موحد للاستجابة.

### 2.2 طبقة التطبيق (Application Layer)
- `Actions / UseCases`: تمثل سيناريوهات واضحة مثل:
  - `CreateCaseAction`
  - `AssignLawyerToCaseAction`
  - `RecordInvoicePaymentAction`
- كل Action ينسق بين النماذج والخدمات ويطبق قواعد العمل.

### 2.3 طبقة النطاق (Domain Layer)
- كيانات النطاق: القضايا، الجلسات، الإجراءات، الفواتير، التحصيل.
- خدمات نطاق (Domain Services): القواعد المعقدة العابرة للكيانات.
- سياسات النطاق (Policies): التحقق من حق المستخدم في تنفيذ عملية معينة.

### 2.4 طبقة البنية التحتية (Infrastructure Layer)
- Eloquent Models + Migrations.
- Queue/Jobs/Events.
- Integrations (Email/SMS/Calendar/Webhooks/Storage).
- Cache + Rate limiting + Logging.

## 3) التقسيم المعياري (Module Boundaries)

### 3.1 Auth & Identity
- تسجيل دخول/خروج، إصدار Token، إدارة الجلسات.
- إدارة المستخدمين والأدوار والصلاحيات (RBAC).
- دعم MFA مستقبلًا ضمن نفس الوحدة.

### 3.2 Cases (القضايا)
- إنشاء القضية وربطها بالعميل/المحكمة/المحامي.
- إدارة الحالة (Workflow state): جديد → جارٍ → مؤجل → مغلق.
- سجل زمني موحد لكل الأحداث المتعلقة بالقضية.

### 3.3 Sessions & Procedures
- إدارة الجلسات القانونية وتواريخها ونتائجها.
- إدارة الإجراءات (Procedures) وربطها بالقضية والموظف المسؤول.
- ربط التذكيرات والتنبيهات بالمواعيد.

### 3.4 Documents
- رفع ملفات آمن (Local/S3-compatible).
- Metadata موحدة: نوع الملف، المصدر، الارتباط بالقضية/العميل.
- مسار مراجعة/اعتماد للمستندات الحساسة (اختياري مرحليًا).

### 3.5 Finance
- الفواتير، المدفوعات، الإيرادات، المصروفات.
- قواعد محاسبية واضحة (حالات الفاتورة + تسوية المدفوعات).
- تجهيز endpoints للتقارير المالية لاحقًا.

### 3.6 Notifications
- قنوات متعددة: داخل النظام + Email (ثم SMS/WhatsApp).
- رسائل مبنية على Events (مثال: قرب موعد جلسة).
- قابلية إعادة المحاولة والفشل المراقب عبر Queue.

### 3.7 Search & Reporting
- بحث سريع عبر جداول مرجعية أساسية.
- Endpoints تقارير تشغيلية (قضايا نشطة، جلسات اليوم، تحصيلات).
- فصل استعلامات التقارير الثقيلة عن CRUD الأساسي.

## 4) هيكل المجلدات المقترح (Laravel)

```text
app/
  Domain/
    Cases/
    Finance/
    Documents/
    Notifications/
  Application/
    Cases/Actions/
    Finance/Actions/
  Http/
    Controllers/Api/V1/
    Requests/
    Resources/
  Policies/
  Services/Integrations/
  Jobs/
  Events/
  Listeners/
```

> الهدف من هذا الهيكل هو تقليل تداخل المسؤوليات، وتسهيل الاختبار، وتمكين فرق متعددة من العمل المتوازي.

## 5) دورة البيانات (Data Lifecycle)

1. العميل يرسل طلب API.
2. `FormRequest` يتحقق من البنية والقيود الأساسية.
3. `Controller` يستدعي `Action` مناسب.
4. `Action` يطبق قواعد النطاق ويجري عمليات DB داخل Transaction عند الحاجة.
5. يتم إطلاق Event عند نجاح العملية.
6. `Resource` يرجع استجابة موحدة للـ Frontend.
7. `Job` غير متزامن يتكفل بالإشعارات/التكاملات الثقيلة.

## 6) قاعدة البيانات: قواعد تأسيسية

- اعتماد **UUID/ULID** للكيانات الأساسية المعرضة خارجيًا.
- فهارس إلزامية على الحقول الأكثر استخدامًا في البحث (`case_number`, `client_id`, `session_date`, ...).
- أعمدة تدقيق موحدة: `created_by`, `updated_by` حيث تنطبق.
- Soft Deletes للكيانات ذات الأثر القانوني.
- جداول Pivot واضحة للعلاقات متعددة-لمتعددة مع قيود فريدة (Unique constraints).

## 7) الأمان والحوكمة

- Laravel Sanctum (أو Passport عند الحاجة لـ OAuth كامل).
- RBAC عبر `roles`, `permissions`, و`role_user`.
- سياسات وصول دقيقة (Policy لكل مورد رئيسي).
- تدقيق العمليات الحساسة: تعديل حالة قضية، حذف مستند، تسوية مالية.
- Rate limiting على endpoints الحساسة (Auth, Search, Export).

## 8) استراتيجية التنفيذ المرحلي (Backend First Roadmap)

### المرحلة 1: Foundation
- إعداد Auth + Users + Roles + Permissions.
- توحيد Error handling وAPI response envelope.
- تجهيز Logging/Audit baseline.

### المرحلة 2: Core Legal Flow
- Cases + Sessions + Procedures (CRUD + Policies + Filters).
- ربط الأحداث الأساسية بإشعارات داخلية.
- كتابة اختبارات Feature حرجة.

### المرحلة 3: Documents + Finance
- رفع/تنظيم المستندات.
- الفواتير والمدفوعات والتقارير الأولية.
- Jobs للعمليات غير المتزامنة.

### المرحلة 4: Integrations + Hardening
- Email/SMS/Webhooks.
- تحسين الأداء (Indexes, Caching, query tuning).
- سيناريوهات E2E وتثبيت مقاييس SLO.

## 9) تعريف Done (لكل وحدة Backend)

تُعتبر الوحدة "جاهزة" عندما تحقق:

- API contracts موثقة وواضحة.
- تغطية اختبار Feature للمسارات الأساسية + حالات التفويض.
- سياسات أمان مفعّلة.
- Observability كافية (Logs + metrics للأخطاء المهمة).
- Migration آمنة وقابلة للتراجع.

## 10) ما الذي يستلمه فريق الـ Frontend بعد انتهاء كل مرحلة؟

- ملف OpenAPI/Swagger محدث.
- أمثلة Responses معيارية.
- قائمة صلاحيات endpoint-by-endpoint.
- بيئة staging مستقرة ببيانات seed واقعية.

---

بهذا الترتيب، تبدأ المنصة من نقطة قوة: **بيانات متماسكة + قواعد عمل محكمة + APIs مستقرة**، مما يقلل إعادة العمل عند بناء الواجهة الأمامية ويزيد جودة المنتج النهائي.
 بناءً على تقرير تحليل الصفحة الرئيسية (Landing Page) لموقعك، إليك خطة التطوير لتحديث وتحسين الهيكلية:

1. أهداف التطوير:

تحسين التنظيم الهيكلي: نقل المحتوى النصي من الصفحة إلى ملفات locales لمزيد من القابلية للتوسّع.

التخصيص حسب حالة المستخدم: تحسين الانتقال بين حالة "زائر" و"مستخدم مسجّل" عبر تحسين واجهات المصادقة.

التفاعل المتقدم: إضافة المزيد من الحركات التفاعلية (animations) والمحتوى المتغير بناءً على بيانات المستخدم.

2. المكونات الأساسية للتطوير:
2.1. تعديل الهيكل العام للـ Landing Page

Hero Section (واجهة المقدمة):

تحسين استخدام motionVariants في framer-motion لإضافة تأثيرات ديناميكية أكبر على النصوص والصور.

استخدام صورة خلفية متميزة يتم تحميلها من fichier assets بشكل مركزي.

إضافة CTA رئيسية/ثانوية تتغير بناءً على حالة المصادقة.

Services Section (الخدمات الأساسية):

استخدام Cards لتوضيح الخدمة مع تأثيرات تحريك إضافية عند التفاعل (hover).

إمكانية إضافة إحصائيات ديناميكية تُحدّث مباشرةً من الـ Backend (مثل عدد القضايا المعالجة).

Why Avocat Section (لماذا أفوكات):

تحسين العرض البصري لبطاقات القيمة الثلاث مع إضافة نصوص مؤثرة تتعلق بالأمان والخدمات المتميزة.

CTA Section (دعوة إجراء نهائية):

تحسين الزر الذهبي لإظهار تأثيرات CSS مع gradient-gold لتحسين التجربة البصرية.

Trust Metrics Section (مؤشرات الثقة):

تحديث المؤشرات بحيث يتم جلبها ديناميكيًا من Backend.

Footer (التذييل):

إضافة روابط لصفحات حول المكتب، السياسة القانونية، شروط الاستخدام.

2.2. تخصيص المحتوى للزوار والمستخدمين المسجلين:

النصوص:

نقل النصوص الثابتة (مثل النصوص التعريفية) إلى ملفات locales لسهولة الترجمة والصيانة.

استخدام نظام i18n (ترجمة النصوص) لتمكين التبديل السلس بين اللغات.

الأزرار والتوجيه:

تفعيل الأزرار وفقًا لحالة المصادقة: زر "تسجيل الدخول" و"إنشاء حساب" للزوار، وزر مباشر لـ "/dashboard" للمستخدمين المسجلين.

2.3. تحسين تجربة المستخدم (UX)

التفاعل المتقدم:

إضافة تأثيرات حركية (motion) لتحسين التفاعل في الأقسام مثل Hero و Services Section باستخدام framer-motion.

إضافة تأثيرات scale/opacity للصورة الرئيسية لتحسين التجربة التفاعلية.

التفاعل مع النصوص والصور:

الصور: استخدام Lazy Load لتحسين تحميل الصور التي تظهر في الـ Hero والـ Services section.

تحسين الانتقال بين الصفحات: استخدام react-router-dom بنمط ديناميكي للانتقال بين صفحات الدخول، التسجيل، واللوحة الرئيسية (Dashboard).

2.4. تحسين الأمان والمرونة في الواجهة

التبديل بين الأنماط (Themes): ضمان أن ThemeToggle يعمل بشكل سلس بين الوضع الفاتح والداكن.

اللغة (Language): تحسين واجهة التبديل بين اللغات العربية والإنجليزية باستخدام LanguageContext لضمان تجربة مستخدم مريحة (RTL و LTR).

2.5. ملاحظات التحسينات المستقبلية:

إدارة الأصول (Assets):

توحيد إدارة الصور والرموز (مثل الـ LandingPageImg و BackgroundSvg) داخل فهرس أصول موحد.

إضافة متغيرات جديدة:

الاستفادة من copy.hero.highlight في تطوير النصوص التعريفية المتميزة في الـ Hero.

تحسين الاتصال بين الـ Frontend و Backend:

استخدام React Context لتحسين إدارة حالة المصادقة بشكل مركزي عبر الصفحات.

3. خطوات التنفيذ:

التهيئة الأولية: تنظيم النصوص داخل ملفات locales للمحتوى المتعدد اللغات.

التطوير في الـ Frontend: تحسين هيكل الصفحة عبر تعديل الـ HomePage.jsx لإضافة الحركات المتقدمة والتفاعل بناءً على الحالة.

التطوير في الـ Backend: إضافة API لجلب البيانات الإحصائية والديناميكية مثل Trust Metrics.

اختبار التفاعل بين الـ Frontend و Backend: التأكد من سلامة البيانات المدخلات والمعالجة في النظام.

تحسين الأمان: إضافة طبقات أمان جديدة للصفحات مثل MFA و التشفير.

خلاصة:

المشروع سيتطلب توحيد النصوص داخل ملفات locales لضمان قابلية التوسّع.

سيكون هناك تحسينات إضافية على الحركات التفاعلية و التخصيص حسب حالة المستخدم لضمان تجربة مستخدم متكاملة وسلسة.

إضافة تحسينات أمنية، مثل MFA وحماية البيانات، مما يعزز التفاعل والثقة في النظام.
