 
# تقرير دقيق للبنية الأمامية (Frontend) — Avocat

## 1) ملخص تنفيذي
الواجهة الأمامية في مشروع **Avocat** مبنية على **React + Vite**، مع توجيه عبر `react-router-dom`، وإدارة حالة هجينة بين **Context PI** و **Redux Toolkit**، مع تنظيم قائم على الوحدات (Features) لتسهيل التوسع والصيانة. نقطة الدخول تقوم بتركيب مزودي السياق لرئيسيين (اللغة، التنبيهات، المصادقة، الأمن) قبل تحميل التطبيق.  

البنية الحالية مناسبة للبدء فوراً بتطوير الواجهة الأمامية، لأنها تحتوي بالفعل على:
- قشرة تطبيق واضحة (App Shell + Dashboard).
- نظام توجيه محمي بالصلاحيات.
- طبقة خدمات API موحدة.
- تنظيم ملفات واضح يفصل بين `features` و `shared`.

---

## 2) نقطة الدخول وسلسلة التهيئة
**نقطة الدخول:** `src/main.tsx`

عند الإقلاع، يتم إنشاء `createBrowserRouter` بمسار جذري، ثم لف التطبيق بعدة Providers بالترتيب التالي:
1. `LanguageProvider`
2. `AlertProvider`
3. Redux `Provider`
4. `AuthProvider`
5. `SecurityProvider`
6. `RouterProvider` داخل `Suspense`

هذا التسلسل يعطي أفضلية للوظائف المشتركة (اللغة/التنبيه/المصادقة/الأمن) قبل تحميل الشاشات، ويضمن أن الحراسة الأمنية تعمل مبكراً.

---

## 3) طبقة التوجيه (Routing) وحماية الوصول
### 3.1 المستوى الأعلى — `src/app/App.tsx`
التطبيق يقسم المسارات الأساسية إلى:
- `/` صفحة رئيسية.
- `/login` و`/signup` مع Redirect إذا كان المستخدم مسجلاً.
- `/dashboard/*` مسارات داخلية محمية عبر `RequireAuth`.
- مسار fallback يعيد إلى الصفحة الرئيسية.

كما يتم تغليف المسارات الداخلية بمزودي الثيم، السايدبار، والـ Spinner.

### 3.2 مسارات لوحة التحكم — `src/app/routes/AuthRoutes.jsx`
داخل `/dashboard/*` يتم تحميل الشاشات بطريقة **Lazy Loading** لتقليل حجم الحزمة الابتدائية وتحسين الأداء.  
كل مسار حساس محاط بـ `PermissionGuard` عبر مكوّن `Guarded`، ويرتبط بخريطة صلاحيات مركزية `permissionMap`.

أمثلة وحدات فعالة ضمن المسارات:
- العملاء وخدمة العملاء.
- القضايا والخدمات القانونية.
- التقارير.
- المالية.
- الإعدادات.
- الإدارة (المستخدمون/الأدوار/الصلاحيات).

النهج المستخدم حالياً ممتاز لتطبيق يعتمد RBAC لأنه يربط **التوجيه + الصلاحية + اسم الوحدة** في مكان واحد.

---

## 4) إدارة الحالة (State Management)
### 4.1 الحالة العالمية الخفيفة عبر Context
داخل `src/shared/contexts` توجد سياقات مسؤولة عن:
- المصادقة `AuthContext`
- اللغة `LanguageContext`
- الثيم `ThemeContext`
- التنبيهات `AlertContext`
- الشريط الجانبي `SidebarContext`
- مؤشر التحميل `SpinnerContext`

هذا مناسب للحالات العرضية والعابرة بين الشاشات.

### 4.2 Redux Toolkit لحالات المجالات
يوجد Store في `src/app/store/store.js` مع Slice خاص بالعملاء `clientsSlice.js` يتضمن:
- بيانات العملاء.
- loading/error.
- async actions لجلب وتحديث الحالة عبر API.

الخلاصة: المشروع يستخدم **نمطاً هجيناً عملياً**: Context للحالات العامة + Redux للبيانات الأكثر تعقيداً وقابلية للتوسع.

---

## 5) طبقة التكامل مع الـ API
طبقة الاتصال الخلفي موجودة في:
`src/shared/services/api/*`

وتتضمن ملفات متخصصة لكل نطاق (عملاء، قضايا، تقارير، محاكم، مصاريف، جلسات...).  
هذا يفصل منطق الشبكة عن الواجهات ويسهّل:
- إعادة الاستخدام.
- الاختبار.
- توحيد إعداد Axios عبر `axiosConfig.js`.

---

## 6) الهيكلية المجلدية المعتمدة
الهيكلية الفعلية تدعم تقسيم واضح:
- `src/app`: التطبيق الأساسي، التوجيه، المتجر.
- `src/features`: الوحدات الوظيفية (قضايا، تقويم، تقارير، مالية...).
- `src/shared`: المكونات المشتركة، الخدمات، السياقات، الحماية، الأنواع.
- `src/styles` + `src/shared/styles`: طبقات التنسيق والـ tokens.
- `public`: أصول ثابتة وأيقونات وخطوط.

هذه البنية مناسبة جداً لفرق متعددة، لأن كل فريق يمكنه امتلاك Feature دون كسر الأجزاء الأخرى.

---

## 7) البنية الأمنية في الواجهة
يوجد مستوى أمني واضح على الواجهة عبر:
- `SecurityProvider`.
- `PermissionGuard`.
- خرائط صلاحيات مركزية (مثل `permissionMap`).

مهم: الحماية في الواجهة هي **تجربة استخدام** ومنع عرض عناصر غير مصرح بها، لكن يجب دائماً أن تتكامل مع تحكم نهائي من الـ Backend وهو النمط الصحيح).

---

## 8) البنية التقنية والبناء (Build)
من `vite.config.js`:
- دعم PWA عبر `vite-plugin-pwa`.
- ضغط ملفات الإنتاج (`vite-plugin-compression`).
- تقسيم حزم vendor.
- aliases منظمة (`@app`, `@features`, `@shared`...).

هذا يقلل زمن التطوير ويجعل الاستيراد أوضح ويجهز المشروع للتوسع.

---

## 9) تقييم الجاهزية للبدء بالواجهة الأمامية
**نعم، يمكن البدء مباشرة بالـ Frontend** لأن الركائز الأساسية جاهزة:
- توجيه محمي.
- هيكلية Features.
- خدمات API.
- سياقات مشتركة.
- إعدادات بناء حديثة.

### أولويات تنفيذ مقترحة (Sprint 0)
1. توحيد معايير كتابة المكونات (TS/JS، naming، lint rules).
2. اعتماد نمط موحد لجلب البيانات (React Query أو الاستمرار بالنهج الحالي مع توثيق موحد).
3. توحيد تصميم صفحات القوائم/التفاصيل عبر Components مشتركة.
4. إكمال توثيق خريطة الصلاحيات UI ↔ API.
5. إضافة اختبارات smoke لمسارات dashboard الأساسية.

---

## 10) خاتمة
البنية الأمامية الحالية ليست مجرد بداية مبدئية، بل **أساس قوي للإنتاج** إذا تم ضبط التوحيد والاختبارات مبكراً.  
الهيكل الحالي يسهل نمو التطبيق إلى نظام قانوني متكامل دون إعادة هيكلة جذرية لاحقاً.
